# 向量库持久化 —— 使用场景、原理、选型对比、延伸八股（测试增量更新）

> 对应代码：`store.py`（核心逻辑）、`main.py`（调用方）、`requirements.txt`（依赖）。
> 关联概念见 `my_code/interview` 仓库的 `12-补充-检索与RAG.md`（检索链路全貌）。

## 一、使用场景与目的

### 1.1 要解决的问题

改造前，`store.py` 用的是 `InMemoryVectorStore`——只存在进程内存里的一个
`dict + numpy 矩阵`。这意味着**每次运行 `main.py` 都要把全部语料重新向量化一遍**：

```
main.py 启动
  → loader.load_documents()      读 20 个文件（不联网，快）
  → chunker.chunk_documents(...) 切成 843 个块（不联网，快）
  → build_store(chunks)          843 块逐个调 embedding API（联网，慢，花钱）
```

实测：843 块全量向量化耗时约 **54~69 秒**，且每次都产生一次真实的 API 调用费用。
但绝大多数时候，笔记内容和上一次运行相比**根本没变**——这部分开销是纯浪费。

### 1.2 目的

把"算好的向量"**落盘**，下次启动时：

- 如果语料没变 → 直接从磁盘读回索引，跳过全部 embedding API 调用
- 如果语料变了 → 照常重新构建，并把新结果存盘供下次复用

实测效果（本项目 843 块规模）：

- 首次构建：约 54 秒（正常，无法避免的一次性成本）
- 命中缓存：约 **7 秒**（只剩读文件+切分+对当前问题做一次 `embed_query` 的时间）

### 1.3 适用边界

这个方案对"语料相对静态、单机跑、单人使用"的场景（比如本项目：一个人维护的
面试笔记库）非常合适。如果换成"多人同时读写、语料分钟级更新"的场景，本文的
"整体重建"策略就不够用了，需要增量更新（见 5.3）。

## 二、底层实现原理

### 2.1 向量库到底存了什么

不管用什么实现，向量库本质上存的是一批三元组：

```
id ──┬── vector    [0.12, -0.87, ..., 0.05]     参与相似度计算
     ├── text      "【xxx.md】...正文..."         参与相似度计算（被压成 vector 的原料）
     └── metadata  {"source": ..., "title_path": ...}   不参与计算，只用于过滤/展示
```

`InMemoryVectorStore` 和 `Chroma` 实现的是同一个 LangChain `VectorStore` 抽象接口
（`similarity_search_with_score` 等方法签名一致），区别只在于**物理存储介质**：
前者是进程内存里的 numpy 矩阵，后者是本地的 sqlite 文件。这也是本项目当初先用
`InMemoryVectorStore` 起步的原因——接口一致，换底层实现时业务代码（`chain.py`、
`tools.py`）完全不用改。

### 2.2 指纹机制：怎么判断"要不要重建"

核心问题：**光有持久化还不够**，必须能判断"磁盘上存的索引是不是还对得上当前语料"。
不判断的话会有两种坏后果：

- 语料明明变了，却一直读旧索引 → 查到的是过时内容，且**不报错**（静默 bug，
  和 `12-补充-检索与RAG.md` 2.2 节讲的"embedding 模型换了但维度相同不报错"是同一类坑）。
- 语料没变，却每次都重建 → 白白浪费时间和钱，持久化形同虚设。

解决办法是给语料算一个"指纹"（内容哈希）：

```python
def compute_fingerprint(chunks: list[Document]) -> str:
    hasher = hashlib.sha256()
    ordered = sorted(chunks, key=lambda d: (d.metadata["source"], d.metadata["title_path"]))
    for doc in ordered:
        hasher.update(doc.metadata["source"].encode("utf-8"))
        hasher.update(doc.metadata["title_path"].encode("utf-8"))
        hasher.update(doc.page_content.encode("utf-8"))
    return hasher.hexdigest()
```

几个设计细节，都是"防止静默出错"的具体落实：

- **先排序再哈希**：`hashlib` 是逐字节累加的，输入顺序变了，哈希结果就变了。
  `loader.find_markdown_files` 本身已经 `sorted()` 过，这里再排一次是双保险——
  不依赖上游的顺序保证。
- **哈希对象是切分后的 chunk，不是切分前的原文**：这样不仅能感知"笔记内容改了"，
  连"以后调整 `chunker.py` 的切分参数（比如改 `MAX_CHARS`）导致切出来的块变了"
  也能被感知到。覆盖面更全，而且切分这一步不联网、很快，不增加成本。
- **哈希算法选 SHA-256（内容哈希）而不是 mtime（文件修改时间）**：
  mtime 是操作系统维护的旁路信息，不是内容本身的属性——`git checkout` 之类的
  操作可能改变 mtime 但不改变内容，也可能相反，会导致误判。内容哈希只要有
  一个字节不同就必然不同，不存在"看起来没变但其实变了"的风险。代价是必须先
  读完全部文件内容才能判断，但 20 篇笔记这个规模，读取本身是毫秒级的，
  相对于后面的 embedding API 调用（几十秒）完全可以忽略。

指纹存取：

```python
def _read_saved_fingerprint() -> str | None:
    path = config.INDEX_DIR / FINGERPRINT_FILE
    if not path.exists():
        return None
    return path.read_text(encoding="utf-8").strip()

def _write_fingerprint(fingerprint: str) -> None:
    config.INDEX_DIR.mkdir(parents=True, exist_ok=True)
    (config.INDEX_DIR / FINGERPRINT_FILE).write_text(fingerprint, encoding="utf-8")
```

指纹文件（`index/fingerprint.txt`）就存在索引目录里，跟向量数据放一起，逻辑上
是"这份索引的身份证"。

### 2.3 三个协作函数 + 一个统一入口

```
load_or_build_store(chunks)         ← main.py 只调这一个函数
    │
    ├─ 算出当前指纹，跟磁盘上存的比较
    │
    ├─ 一致 → load_existing_store()         直接 Chroma(persist_directory=...) 打开
    │                                        （不重新向量化，不联网）
    │
    └─ 不一致 → build_store(chunks, fingerprint)
                    Chroma.from_documents(chunks, embedding=..., persist_directory=...)
                    调 embedding API 重新向量化，写盘，并调 _write_fingerprint()
```

`build_store` 和 `load_existing_store` 用的是 Chroma 的两条不同入口：

- `Chroma.from_documents(docs, embedding=...)` —— "给我文档，我建索引"，
  参数名是 `embedding`。
- `Chroma(embedding_function=...)` —— "我不建，只是打开已有的"，
  参数名是 `embedding_function`。这两个名字不一样是 Chroma 自己 API 的设计，
  容易打错，打错了会直接 `TypeError`（这算是好事，能立刻发现问题，
  不会静默出错）。

`load_existing_store` 里传的 `embedding_function=get_embeddings()` 只是"记住
以后查询时用哪个模型"，本身不触发任何网络请求——真正调 API 是 `search()`
对用户的问题做 `embed_query()` 那一刻才发生。这也是为什么"读盘"分支只要
7 秒（一次 `embed_query` + 一次对话模型调用），而不是完全 0 秒。

### 2.4 一个容易踩的坑：分数含义反转

`InMemoryVectorStore.similarity_search_with_score` 返回**余弦相似度**
（分数越大越相似，0~1 之间）。Chroma 官方 docstring 写得很明确：

> `Lower score represents more similarity.`

Chroma 默认返回的是**距离**（分数越小越相似）。这是两个库返回值语义上的
真实反转，如果项目里有代码依赖"分数越大越靠前"做排序或者展示（比如
"相关度 0.92"这种文案），换库后必须跟着改，否则输出会产生误导性的文案
（本项目在改造时就发现 `main.py` 里"相关度 {score}"这行文案需要改成
"距离 {score}（越小越相关）"）。

这类问题的通用教训：**换底层实现库时，除了看接口签名是否兼容，还要看
返回值的语义是否一致**——签名一样不代表数值含义一样。

## 三、竞对方案及优缺点对比

### 3.1 向量存储方案横向对比

| 方案                                              | 存储介质                                 | 持久化            | 部署成本                             | 适合规模         | 备注                                                                                                |
| ------------------------------------------------- | ---------------------------------------- | ----------------- | ------------------------------------ | ---------------- | --------------------------------------------------------------------------------------------------- |
| **InMemoryVectorStore**（改造前）           | 进程内存（numpy）                        | ❌ 无             | 零依赖                               | 小规模、临时验证 | 本项目的起点，胜在"零成本切换到别的 VectorStore"                                                    |
| **Chroma**（本次选型）                      | 本地 sqlite 文件                         | ✅ 本地落盘       | 单机嵌入式，约 50MB 依赖             | 几万到百万级     | 不用起独立服务进程，最适合个人/单机项目                                                             |
| **FAISS**                                   | 内存 + 手动落盘（`faiss.write_index`） | 需自己管理        | 中等，需自己维护 id-metadata 映射    | 百万到十亿级     | 检索性能强，但索引和元数据是分离的，langchain 封装之外要自己处理映射关系，工程量比 Chroma 大        |
| **pgvector**（Postgres 扩展）               | Postgres 数据库                          | ✅ 数据库级持久化 | 依赖一个 Postgres 实例               | 百万级以内很舒服 | 如果数据本来就在 Postgres 里，几乎是免费的能力；能和业务表同事务，强一致；支持 SQL 原生的元数据过滤 |
| **Milvus / Qdrant / Weaviate** 等专用向量库 | 各自的分布式存储                         | ✅                | 高——需要独立部署运维一个分布式系统 | 千万到亿级       | 功能最全（PQ 压缩、DiskANN 磁盘索引、原生分布式），但对个人项目是过度设计                           |

### 3.2 为什么这个项目选 Chroma

- **规模**：843 个 chunk，未来即使笔记翻十倍也就几千到一万块，远够不上
  "百万级"这个需要专用向量库的门槛。
- **部署成本**：不想额外起一个 Postgres 或分布式服务，Chroma 是进程内嵌式的，
  `pip install` 之后直接可用，这点和 `InMemoryVectorStore` 的"零依赖"哲学一脉相承，
  只是多了个"能落盘"的关键能力。
- **接口一致性收益**：`langchain_core.VectorStore` 这层抽象在切换时体现了价值——
  `store.py` 里 `search()` 函数一行没改，只是构造函数从 `InMemoryVectorStore.from_documents`
  换成了 `Chroma.from_documents` / `Chroma(...)`。

如果这个项目以后要多人协作、语料要频繁远程更新、规模冲到百万级，
应该重新评估——大概率会走向 pgvector（如果团队本来就用 Postgres）或
Milvus/Qdrant（如果追求极致的检索性能和分布式扩展）。

### 3.3 判断标准（通用结论）

> 数据本来就在 Postgres 里 + 规模百万级以内 → **用 pgvector，别上专用库**。
> 多引入一个系统带来的运维复杂度、数据同步问题、团队学习成本，
> 通常远大于那点性能收益。

这是行业内比较公认的判断标准（参见 `12-补充-检索与RAG.md` 2.3 节），
本项目虽然没有 Postgres，但精神是一致的：**优先选运维成本最低、能满足当前
规模的方案，不为性能过度设计**。

## 四、延伸技术栈八股（面试高频）

### Q1：为什么 embedding 模型和维度必须绑定，不能中途换？

因为 embedding 模型是把文本映射到**它自己训练出来的**向量空间。两个模型的
空间之间没有对齐关系——模型 A 里"猫"的向量和模型 B 里"猫"的向量之间的
余弦相似度是没有意义的噪声。

三个具体后果：

- **索引和查询必须用同一个模型**。升级 embedding 模型 = 全量重建索引，
  这是 RAG 系统最贵的一次迁移，选型时就要考虑"以后能不能换得动"。
- 维度不同（比如 768 vs 1536）→ 矩阵形状不匹配，直接报错——这其实是好事，
  能立刻暴露问题。
- **维度相同但模型不同**（比如都是 1024 维）→ **不报错，静默返回垃圾结果**。
  这是最危险的情况，本项目 `config.py` 专门写了大段注释强调这一点，
  索引里必须隐含地绑定"用哪个模型建的"（本项目通过"只在 config.py 一处
  定义模型名"来规避，没有做显式的模型版本校验，这是可以进一步加固的点）。

### Q2：本项目的指纹机制和"索引新鲜度"问题是什么关系？

`12-补充-检索与RAG.md` 提到语义检索的弱点之一是"更新文档要重新 embed，
索引新鲜度是个工程问题"。本项目的指纹机制就是对这个问题的一个轻量级回答：
**不做增量更新，但至少能自动判断"该不该整体重建"**，避免了两个极端——
要么每次都重建（浪费），要么从不重建（索引过时）。

代价是"改一个字也要全量重建"，这在语料规模小（几百到几千块）时完全能接受；
规模大了之后，就需要更精细的增量更新策略（见 5.3）。

### Q3：为什么要用"内容哈希"而不是给每个文件存一个"版本号"？

版本号需要一个额外的记账系统（谁来在文件变化时递增版本号？），而且容易和
实际内容脱节（版本号忘了改，但内容其实变了）。内容哈希是**自证的**——
哈希值本身就是从内容直接计算出来的，不需要额外维护任何状态，不可能出现
"版本号说没变、内容其实变了"这种不一致。这是"用可验证的推导代替手工维护
的状态"这一设计原则的具体体现。

### Q4：pgvector 和专用向量库的核心权衡是什么？

参考对比表（3.1），核心权衡就是"生态整合"vs"检索性能上限"：

- pgvector 的杀手锏是**能和业务数据同库同事务**——一条 SQL 里同时做
  `WHERE` 结构化过滤 + 向量排序 + 全文检索，向量和业务数据永远一致，
  不存在"向量库和主库不同步"的分布式一致性问题。
- 专用库的杀手锏是**规模和检索算法的丰富度**——支持 PQ 量化压缩、
  DiskANN 磁盘索引等技术，能撑到十亿级向量，pgvector 撑不到这个量级。

选型的本质问题不是"哪个技术更好"，而是"你的规模有没有到不得不用专用库
的地步，以及你是否愿意为此承担独立运维一个分布式系统的成本"。

### Q5：ANN（近似最近邻）是什么，为什么向量数据库都要用它？

暴力检索（拿查询向量和库里每个向量都算一遍余弦相似度）的复杂度是 `O(N × d)`。
`N` = 向量数量，`d` = 向量维度。当 `N` = 100 万、`d` = 1536 时，一次查询要做
几十亿次浮点运算，延迟在几百毫秒到几秒之间，且查询量一上来系统就顶不住。

ANN（Approximate Nearest Neighbor）用可控的一点点精度损失换几个数量级的
速度提升——比如召回率从 100% 降到 95%，换来 100 倍加速，这笔交易在几乎
所有 RAG 场景下都划算。Chroma、pgvector、Milvus 等主流向量库底层都会提供
HNSW（多层图、常见默认）或 IVF（聚类倒排）这类 ANN 索引算法。
（HNSW/IVF 的具体原理、参数取舍见 `12-补充-检索与RAG.md` 2.3 节，
本项目当前 843 个块的规模远用不上手动调 ANN 参数——Chroma 内部默认
配置已经足够，等语料规模冲到十万级以上才需要关心这个。）

### Q6：为什么"换向量库只改一行代码"是值得追求的设计目标？

这体现的是面向接口编程（而不是面向具体实现编程）的价值。本项目从一开始
就用 LangChain 的 `VectorStore` 抽象类（`from_documents` / `similarity_search_with_score`
这套统一签名），而不是直接手写"造一个 numpy 矩阵、自己算余弦相似度"。
代价是多了一层抽象、要学 LangChain 的接口约定；收益是这次换成 Chroma时，
业务逻辑代码（`chain.py`、`tools.py`）一行没有改动，只有 `store.py` 内部
构造向量库的那几行变了。这是"提前预留可扩展点"在实际项目里兑现收益的
一个具体例子，但也要注意：这个收益是有前提的——**换底层实现时接口签名
兼容，不代表返回值的语义一定兼容**（见 2.4 的分数反转教训），抽象只能
屏蔽"怎么调用"，屏蔽不了"结果的含义变了"。

## 五、当前方案的已知局限（留给后续迭代）

1. **不做增量更新**：只要有一个字符变化，就要整体重新向量化全部 chunk。
   当前规模（843 块）下重建约 1 分钟，可接受；规模大了之后需要考虑
   "只重新向量化变化的文件对应的 chunk"。
2. **单机单进程假设**：没有处理多进程/多用户并发写入同一个 `index/` 目录
   的情况（比如两个进程同时判断"指纹变了"并同时重建，可能互相覆盖）。
   对个人学习项目而言不是问题，但如果这个项目要给多人共用，需要加锁或
   改成服务化架构。

## 六、后续改进记录

### 6.1 模型版本校验已加入指纹（2026-09-22）

**问题：** 五.2 提到的"换模型但语料没变，指纹检测不到"这个静默 bug 风险。

**改进：** `store.compute_fingerprint` 现在会先哈希 `config.EMBEDDING_MODEL`
和 `config.EMBEDDING_DIM`，再哈希 chunk 内容。换模型后指纹必然不同，会触发
重建，不再有"旧向量 + 新查询向量"混用的风险。

**代码位置：** `store.py` L43-63

```python
def compute_fingerprint(chunks: list[Document]) -> str:
    hasher = hashlib.sha256()
    # 先哈希模型配置
    hasher.update(config.EMBEDDING_MODEL.encode("utf-8"))
    hasher.update(str(config.EMBEDDING_DIM or "default").encode("utf-8"))
    # 再哈希 chunk 内容
    ...
```

这是一个"防御性设计"——当前还没踩过这个坑（因为还没换过模型），但加上这个
校验的成本几乎为零（多算两次哈希，忽略不计），而它堵住的是一个**静默失败**
（不报错、返回垃圾结果）的风险点，这种 bug 在生产环境最难排查。
