## 二、技术选型与决策点

### 2.1 为什么用混合检索？

**问题背景**：

- **纯向量检索**：擅长语义，但对精确术语不敏感（如"BM25算法"可能召回一堆"检索算法"）
- **纯BM25检索**：擅长精确匹配，但不懂同义词改写（如问"优缺点"，文档里没这个词就完全失败）

**解决方案**：混合检索

```python
# 两路召回
semantic_results = vector_store.search(query, k=20)  # 语义召回
bm25_results = bm25.search(query, k=20)              # 关键词召回
fused = rrf_fusion([semantic_results, bm25_results]) # RRF融合
return fused[:5]                                      # 返回前5个
```

**实验数据证明**：

- 语义改写查询（"优缺点"）：纯BM25完全失败（分数0.0000），混合检索成功
- 精确术语查询（"HNSW"）：三种方法都成功，但混合检索排序最优（MRR 0.7389）

**面试回答模板**：

> "我对比了三种检索方法。纯BM25在'向量检索和关键词检索各有什么优缺点'这个问题上完全失败（分数0.0000），因为笔记里没有直接写'优缺点'这个词。而纯向量虽然能理解语义，但对精确术语不够敏感。最终我用混合检索，让召回率从86.67%提升到93.33%，失败案例从2个降到1个。"

---

### 2.2 RRF 融合算法是什么？

**全称**：Reciprocal Rank Fusion（倒数排名融合）

**核心思想**：

- 不看分数（因为向量距离和BM25分数量纲不同，没法直接比较）
- **只看排名**：第1名、第2名、第3名...
- 对每个文档，RRF分数 = Σ 1/(k + rank_in_each_list)

**公式**：

```
RRF_score(doc) = Σ 1/(k + rank_i)
  其中：
  - k = 60（平滑参数，经验值）
  - rank_i = 该文档在第i路检索中的排名（从1开始）
```

**举例**：
假设文档A：

- 在向量检索中排第1名 → 贡献 1/(60+1) = 0.0164
- 在BM25检索中排第2名 → 贡献 1/(60+2) = 0.0161
- **总分 = 0.0325**

文档B：

- 在向量检索中排第10名 → 贡献 1/(60+10) = 0.0143
- 在BM25检索中未出现 → 贡献 0
- **总分 = 0.0143**

→ 文档A的RRF分数更高，排在文档B前面

**关键特性**：

1. **在两路都排前面的文档 → RRF分数高**（A在两路都靠前，总分高）
2. **只在单路出现的文档 → 也保留但分数低**（B只在一路出现，总分低但不会被丢弃）
3. **无量纲问题**：不需要归一化，直接按排名算

**面试回答模板**：

> "RRF是一种排名融合算法，公式是 1/(k+rank) 的累加。它的好处是不用归一化分数，直接看排名。比如一个文档在向量检索排第1，BM25排第2，它的RRF分数就是 1/61 + 1/62 = 0.0325。在两路都排前面的文档会得到更高的融合分数，这样就能同时利用语义理解和精确匹配的优势。"

### 2.3 召回率（Recall）vs 命中率（Hit Rate）

**区别**：

| 指标                 | 定义                                          | 计算公式                        | 本项目数值               |
| -------------------- | --------------------------------------------- | ------------------------------- | ------------------------ |
| **Hit Rate@K** | 前K个结果中是否**至少命中1个**相关文档  | 命中的问题数 / 总问题数         | **93.33%** (14/15) |
| **Recall@K**   | 前K个结果中召回了**多少比例**的相关文档 | 召回的相关文档数 / 总相关文档数 | 320% (16/5)              |

**为什么Recall > 100%？**

- **同一文档的多个chunk都被检索到**
- 例如："HNSW是什么" 检索到5个结果，全部来自 `12-补充-检索与RAG.md`
- Recall = 5个命中 / 1个标准答案文档 = 500%

**这是bug吗？**

- **不是**，这反映了**文档粒度标注 vs chunk粒度检索**的差异
- 对于集中在某个文档的知识，检索会返回该文档的多个相关段落

**面试官追问："Recall超过100%合理吗？"**

> "合理。我的标注是文档级的（'这个问题的答案在12-补充-检索与RAG.md'），但检索返回的是chunk级的。比如问'HNSW是什么'，检索可能返回该文档的5个不同段落（参数介绍、性能对比、使用场景等），所以Recall是5/1=500%。如果要避免这个现象，可以做文档级去重，或者改用chunk级标注（标注具体哪些段落相关）。"

---

### 2.4 MRR（Mean Reciprocal Rank）

**定义**：第一个相关文档的倒数排名的平均值

**计算公式**：

```
MRR = (1/N) * Σ (1 / rank_i)
  其中：
  - N = 总问题数
  - rank_i = 第i个问题中，第一个相关文档的排名
```

**举例**：

- 问题1：相关文档排第1位 → 1/1 = 1.0
- 问题2：相关文档排第2位 → 1/2 = 0.5
- 问题3：相关文档排第4位 → 1/4 = 0.25
- **MRR = (1.0 + 0.5 + 0.25) / 3 = 0.583**

**本项目数值**：

- 混合检索 MRR = **0.7389**
- 含义：相关文档平均排在第 **1.35** 位（1 ÷ 0.7389 ≈ 1.35）

**面试回答模板**：

> "MRR衡量的是相关文档的排名质量。我们的混合检索MRR是0.7389，意味着相关文档平均排在第1.35位。这比纯BM25的0.6389（第1.56位）要好，说明融合后的排序更准确。"

### 2.5 为什么要做增量更新？

**问题背景**：

- 843个chunk全量向量化耗时 **54秒**
- 但90%的情况下语料并未改变
- 每次启动都重新向量化 = 浪费时间 + 浪费API成本

**解决方案**：文件级指纹 + 增量更新

**实现细节**：

```python
# 1. 给每个文件计算指纹（SHA256哈希）
old_fingerprints = load_from_disk()  # {"12-补充-检索与RAG.md": "a3f2e1...", ...}
new_fingerprints = compute_file_fingerprints(chunks)

# 2. 对比指纹，找出变化的文件
added, modified, deleted = detect_changes(old_fingerprints, new_fingerprints)

# 3. 只重新向量化变化的文件
for changed_file in (added + modified):
    vector_store.delete(where={"source": changed_file})  # 删除旧数据
    new_chunks = [doc for doc in all_chunks if doc.metadata["source"] == changed_file]
    vector_store.add_documents(new_chunks)  # 只向量化这些chunk
```

**效果数据**：

| 场景                | 耗时          | 说明                    |
| ------------------- | ------------- | ----------------------- |
| 首次构建            | ~54s          | 843个chunk全量向量化    |
| 缓存命中            | ~7s           | 直接加载，不调API       |
| 增量更新（1个文件） | ~3s           | 只重建该文件的52个chunk |
| **成本节省**  | **94%** | (54-3)/54 = 94%         |

**指纹覆盖内容**：

```python
hasher.update(EMBEDDING_MODEL)  # 模型名
hasher.update(EMBEDDING_DIM)    # 维度
hasher.update(chunk_content)    # chunk内容
```

→ **换模型也会触发重建**，防止"旧向量+新查询向量"混用的静默bug

**面试回答模板**：

> "我用文件级指纹做增量更新。每个文件算一个SHA256哈希，启动时对比新旧指纹，只重建变化的文件。效果是：首次构建54秒，缓存命中7秒，单文件增量更新3秒，节省94%的向量化成本。指纹里包含了模型名和维度，所以换模型也会触发重建，避免向量不兼容的bug。"

### 2.6 为什么选 Chroma 而不是 Faiss/Milvus？

| 维度                 | Chroma             | Faiss                    | Milvus         |
| -------------------- | ------------------ | ------------------------ | -------------- |
| **部署**       | 本地sqlite，零配置 | 内存only，需自己做持久化 | 需要Docker，重 |
| **元数据过滤** | 原生支持           | 需手写逻辑               | 支持           |
| **增删改**     | 支持按metadata删除 | 不支持，只能重建         | 支持           |
| **规模**       | 适合 <100万        | 适合 >百万               | 适合 >千万     |
| **本项目规模** | 843个chunk         | 843个chunk               | 843个chunk     |

**决策依据**：

1. **规模小**：843个chunk，Chroma完全够用
2. **需要增量更新**：必须支持按文件删除旧数据
3. **本地部署**：不想依赖外部服务，sqlite单文件最简单
4. **快速迭代**：零配置，pip install即用

**面试回答模板**：

> "我选Chroma因为：1）规模小（843个chunk），不需要分布式；2）支持按metadata删除，可以做增量更新；3）本地sqlite持久化，零配置。如果以后扩展到百万级，我会考虑Faiss（单机）或Milvus（分布式）。"

## 三、常见面试问题速答

### Q1: 你的RAG系统和普通的检索有什么区别？

**回答框架**：

1. **普通检索**：返回文档列表（如搜索引擎）
2. **RAG系统**：检索 + 生成，返回自然语言答案，并标注来源

**本项目特色**：

- 混合检索（向量+BM25+RRF）
- Agent架构（ReAct循环，自主决策何时检索）
- 多轮记忆（InMemorySaver，支持追问）
- 引用标注（每条答案标注来源文件）

---

### Q2: 如何评估你的RAG系统效果好不好？

**回答要点**：

1. **准备评估数据集**：15个问题 + 标注相关文档
2. **检索质量指标**：Hit Rate（93.33%）、MRR（0.7389）、Precision、Recall
3. **对比实验**：纯向量 vs 纯BM25 vs 混合检索
4. **分析失败案例**：找出系统弱点，提出改进方向

---

### Q3: 如果检索到的文档不相关，怎么办？

**回答框架**：

1. **诊断原因**：是查询表述问题？还是文档切分问题？还是向量模型问题？
2. **解决方案**：
   - Query改写：用LLM将模糊问题改写成明确的子问题
   - 加入Rerank：用交叉编码器对候选结果重排序
   - 优化切分：让每个chunk保留更多上下文信息
   - HyDE（假设文档嵌入）：先让LLM生成假设答案，再用假设答案去检索

**本项目失败案例**：

- 问题："Agent中的工具系统怎么设计"
- 原因：问题太泛化，面试题库文档语义干扰
- 改进：改写成"Agent如何注册和调用工具"（更具体）

---

### Q4: 你的切分策略是什么？为什么这么切？

**回答要点**：

1. **按Markdown标题层级切分**：保留文档结构
2. **代码块保护**：不在代码块中间切断
3. **段落二次切分**：单段超过800字再切，避免打断论述
4. **合并短块**：<120字的相邻块合并，避免噪声

**参数**：

- MAX_CHARS = 800（一个chunk最多800字）
- MIN_CHARS = 120（太短的块合并）

**实际效果（843个chunks）**：

- **平均大小：589 字符**
- 中位数：641 字符
- 大小分布：
  - 0-200字：4.9%
  - 200-400字：20.6%
  - 400-600字：18.6%
  - **600-800字：36.5%**（最多，符合预期）
  - 800字以上：19.3%（超过上限的，通常是代码块或表格）

**为什么800字？**

- 中文大致 1字 ≈ 1~1.5 token
- 800字 ≈ 600~1000 token
- **实际平均 589 字 ≈ 440~880 token**（落在最佳范围内）
- 既不会太碎（打断论述），也不会太大（向量稀释）

**面试回答模板**：

> "我按Markdown标题层级切分，单个chunk上限800字，太短的（<120字）合并。最终843个chunks，**平均大小589字**（约440~880 token），36.5%的chunk在600-800字这个黄金区间。这个大小既不会打断完整论述，也不会让向量表征太稀疏。"

### Q5: 如果要上生产环境，你会做哪些改进？

**回答框架**：

**稳定性**：

- 异常处理：API超时、向量库崩溃、OOM
- 降级策略：向量检索失败时降级到纯BM25

**性能**：

- 异步化：检索和向量化异步执行

**可观测性**：

- 日志：每次检索记录query、召回文档、耗时
- Tracing：LangSmith追踪每一步
- A/B测试：对比不同配置的效果

## 六、面试高频追问及答案

### 追问1："RRF的k参数怎么选？"

> "k=60是经验值（来自论文）。k越大，排名靠后的文档权重越接近；k越小，排名差距的影响越大。我用的是默认60，如果要调优，可以在评估集上网格搜索k=30/40/50/60/80，选MRR最高的。"

### 追问2："为什么不用重排序模型？"

> "Rerank确实能进一步提升排序质量（预期MRR +0.05~0.10），但会增加推理成本和延迟。当前召回率93.33%已经满足需求，所以暂时没加。如果上生产，我会加Rerank作为可选项，在精度和速度之间做trade-off。"

### 追问3："你的向量维度是多少？为什么？"

> "1024维（模型默认）。降维到512可以省一半存储，但会损失语义信息。我的语料规模小（843个chunk），存储不是瓶颈，所以用全维度保证召回质量。如果扩展到百万级，我会做降维实验，看512维损失多少召回率。"

### 追问4："如何处理多轮对话的上下文？"

> "用LangGraph的InMemorySaver，按thread_id存历史。比如用户先问'HNSW是什么'，再问'它的参数怎么调'，第二个问题的'它'会被正确解析成HNSW。如果上生产，会换成SqliteSaver持久化，并加上滑动窗口限制历史长度。"

### 追问5："你的系统能处理多大规模的数据？"

> "当前843个chunks（~20万字），Chroma + HNSW索引完全够用，检索耗时<100ms。理论上Chroma能撑到几十万chunks。如果扩展到百万级，我会切换到Faiss（单机）或Milvus（分布式），并加上倒排索引做粗排+精排的两阶段检索。"
