## 二、模块一：智能文档切分

### 2.1 问题背景

**为什么要切分？**

向量是对一段文本"求平均"的结果。一篇 15,000 字的笔记讲了 HNSW、BM25、pgvector 十几个话题，压成一个 1024 维向量就成了"这些话题的平均值"——用户问"BM25 公式"，这个"平均向量"根本匹配不上。

**块越小，语义越纯。**

### 2.2 关键技术抉择

#### 抉择 1：按标题切 vs 按字数切

| 方案                 | 优点                   | 缺点                           | 我们的选择 |
| -------------------- | ---------------------- | ------------------------------ | ---------- |
| **按固定字数硬切**   | 实现简单，通用性强     | 破坏语义完整性，标题和正文分离 | ❌         |
| **按标题层级切分**   | 保留语义边界，结构清晰 | 依赖文档结构                   | ✅         |

**为什么选按标题切？**

标题不是排版装饰，是作者亲手划的**语义边界**。作者写 `## 3.1 考勤制度` 时，就是在说"从这里开始讲考勤，到下一个 ## 为止"。这是白送的语义边界，比按字数硬切强得多。

**代码位置：** `chunker.py:49` `split_by_heading()`

---

#### 抉择 2：标题路径放在 page_content vs metadata

| 方案                          | 优点                   | 缺点                               | 我们的选择 |
| ----------------------------- | ---------------------- | ---------------------------------- | ---------- |
| **放在 metadata**             | 干净，不污染正文       | **不参与向量计算**，搜不到         | ❌         |
| **拼进 page_content 开头**    | 参与向量计算，能被召回 | 占用一些字符空间（~30 字）         | ✅         |

**为什么必须拼进 page_content？**

```python
# 向量化过程
embedding = embed_model(doc.page_content)  # 只用 page_content
# metadata 完全不参与向量计算
```

如果标题路径只在 metadata 里：
- 用户问"考勤制度"
- 这一块的 `page_content` 里没有"考勤"两个字
- 向量根本不包含"考勤"的语义 → **搜不到**

**实际效果：**

```
【12-补充-检索与RAG.md】补充 A：检索与 RAG > 2.3 索引与向量库

HNSW（Hierarchical Navigable Small World）是一种多层图索引...
```

标题路径占 30 字，正文 150 字，比例合理。

**代码位置：** `chunker.py:136-140`

#### 抉择 3：代码块保护：状态机 vs 正则提前匹配

| 方案                           | 优点               | 缺点                               | 我们的选择 |
| ------------------------------ | ------------------ | ---------------------------------- | ---------- |
| **正则提前匹配 `r'```.*?```'`** | 一次性匹配所有     | 未闭合代码块会失败，嵌套会错位     | ❌         |
| **状态机逐行扫描**             | 鲁棒性强，处理边界 | 需要维护状态                       | ✅         |

**为什么用状态机？**

Markdown 代码块是**成对出现**的，必须追踪状态：

```markdown
正文
​```python
# 这是代码注释，不是标题
def foo():
    pass
```
正文
```

如果用正则 `re.findall(r'```.*?```', text, re.DOTALL)` 提前匹配：
- 遇到未闭合的代码块（用户笔记写错了）会匹配失败
- 嵌套代码块（Markdown 里展示 Markdown 代码）会匹配错位

**状态机的优势：**

​```python
in_code = False
for line in text.split("\n"):
    if FENCE.match(line):  # ``` 或 ~~~
        in_code = not in_code  # 翻转状态
        continue
    
    if in_code:
        buf.append(line)  # 代码块内部，一律当正文
        continue
    
    # 代码块外面，才判断是不是标题
    if HEADING.match(line):
        # 处理标题逻辑
```

**实测效果：**

- 旧版：551 块里有 **176 块（32%）** 的标题路径被代码注释污染
- 新版（状态机）：**0 块** 错误，准确率 100%

**代码位置：** `chunker.py:59-77`

#### 抉择 4：超长段落二次切分策略

**问题：** 按标题切完后，最长的块有 **5,823 字**（配置上限 800 字的 7 倍）

**原因：** 有些 Markdown 文件的某个标题下内容特别多（如"常见面试题汇总"）

**方案对比：**

| 方案                   | 优点                   | 缺点                       | 我们的选择 |
| ---------------------- | ---------------------- | -------------------------- | ---------- |
| **按句子切（. 或 。）** | 语义更完整             | 中英文混合时边界难判断     | ❌         |
| **按段落切（双换行）** | 实现简单，基本不破坏语义 | 单段落超长时无能为力       | ✅         |
| **不切，保留超长块**   | 避免破坏代码块         | 向量"平均值"问题重现       | ❌         |

**为什么选按段落切？**

段落（`\n\n`）也是语义边界，在段落中间断开会把一句话劈成两半。按段落贪心装箱，既保证语义完整，又不会让单个块过长。

**贪心装箱逻辑：**

```python
def pack(body: str, max_chars: int) -> list[str]:
    pieces = []
    cur = ""
    for para in body.split("\n\n"):  # 按空行切成段落
        if len(cur) + len(para) + 2 <= max_chars:
            cur = f"{cur}\n\n{para}" if cur else para
        else:
            if cur:
                pieces.append(cur)  # 当前块满了，封口
            cur = para  # 这段作为新块的开头
    if cur:
        pieces.append(cur)
    return pieces
```

**边界处理：** 如果某个段落自己就超过 max_chars（长代码块、长表格），会被**原样保留、不再切**——代码块从中间断开比超长更糟。

**代码位置：** `chunker.py:107-128`

## 三、模块二：混合检索架构

### 3.1 问题背景

**单一检索路径有盲区：**

| 检索方式           | 擅长                       | 不擅长                                   | 典型失败案例                                  |
| ------------------ | -------------------------- | ---------------------------------------- | --------------------------------------------- |
| **纯向量检索**     | 语义理解、同义词改写       | 精确术语匹配                             | 问"BM25"，召回"检索算法"但漏掉真正的 BM25 段落 |
| **纯 BM25 关键词** | 精确字面匹配、术语识别     | 语义理解、同义词                         | 问"那个图的东西"，完全抓瞎                    |

**核心矛盾：** 用户问题既可能是"BM25 公式"（需要精确匹配），也可能是"那个图结构快不快"（需要语义理解）。单一路径无法兼顾。

### 3.2 关键技术抉择

#### 抉择 1：混合检索 vs 单一检索

| 方案               | 召回率 | 精确率 | 实现复杂度 | 我们的选择 |
| ------------------ | ------ | ------ | ---------- | ---------- |
| **纯向量检索**     | 中     | 中     | 低         | ❌         |
| **纯 BM25**        | 低     | 高     | 低         | ❌         |
| **混合检索 + 融合** | 高     | 高     | 中         | ✅         |

**为什么选混合检索？**

两路互补，语义 + 字面都能兼顾：
- 向量检索召回"语义相关但措辞不同"的文档
- BM25 召回"字面精确匹配"的文档
- RRF 融合：在两路都排前面的文档 → 最终分数高

**代码位置：** `store.py:380-424`

---

#### 抉择 2：融合算法：RRF vs 加权求和

| 方案                     | 优点                       | 缺点                           | 我们的选择 |
| ------------------------ | -------------------------- | ------------------------------ | ---------- |
| **加权求和**             | 简单直观                   | 需要手动调权重，不同场景最优权重不同 | ❌         |
| **RRF (排名倒数加权)**   | 无需调参，鲁棒性强         | 理解成本稍高                   | ✅         |

**RRF 原理：**

```python
def _rrf_fusion(results_list, k=60):
    """对每个 doc，RRF 分数 = Σ 1/(k + rank_in_each_list)"""
    for results in results_list:
        for rank, (doc, _) in enumerate(results, start=1):
            rrf_scores[doc] += 1.0 / (k + rank)
    return sorted(rrf_scores)
```

**为什么 RRF 比加权求和好？**

1. **无需调参：** k=60 是论文经验值，适用绝大多数场景
2. **排名优先：** 只看排名，不看原始分数（向量相似度和 BM25 分数量纲不同，直接加权没意义）
3. **双路都认可的文档会脱颖而出：**
   - 文档 A：向量排名第 1，BM25 排名第 2 → RRF 分数 = 1/61 + 1/62 = 0.0325
   - 文档 B：向量排名第 10，BM25 排名第 20 → RRF 分数 = 1/70 + 1/80 = 0.0268
   - A > B，双路都认可的文档胜出

**k=60 怎么来的？**

来自论文 *Reciprocal Rank Fusion outperforms Condorcet*，经验值。
- **k 越大** → 排名差异的权重差越小，更"平等"
- **k 越小** → 头部排名的权重越大，更"集中"

**代码位置：** `store.py:347-378`

---

#### 抉择 3：动态 top-k 策略

**问题：** 直接返回向量 top-5 + BM25 top-5 融合吗？

**不行！** 如果两路召回的文档重叠度低，RRF 融合会让"只在单路出现的文档"分数过低，导致最终 top-5 都是"双路都有但排名不高"的文档。

**解决方案：两阶段检索**

```python
FETCH_K = 20  # 第一阶段：每路召回 20 个
TOP_K = 5     # 第二阶段：融合后取前 5 个
```

| 阶段       | 目标                           | 参数        |
| ---------- | ------------------------------ | ----------- |
| **第一阶段** | 给融合算法足够的选择空间       | FETCH_K=20  |
| **第二阶段** | 保持结果紧凑，避免信息过载     | TOP_K=5     |

**为什么是 20 和 5？**

- 20：经验值，足够大（覆盖更多候选），但不至于引入太多噪声
- 5：LLM 上下文窗口有限，5 个文档约 900 字，刚好够生成一个完整回答

**代码位置：** `store.py:405-406`

#### 抉择 4：BM25 分词策略（中文 + 专有名词）

**问题：** 中文没有天然的词边界，怎么分词？

**方案对比：**

| 方案                           | 例子                                       | 优点         | 缺点                       | 我们的选择 |
| ------------------------------ | ------------------------------------------ | ------------ | -------------------------- | ---------- |
| **jieba 分词**                 | "HNSW 的 M 参数" → ["HNSW", "的", "M", "参数"] | 准确率高     | 依赖词典，专有名词可能被切碎 | ❌         |
| **单字切分**                   | "HNSW 的 M 参数" → ["H", "N", "S", "W", "的", "M", "参数"] | 通用性强     | 专有名词被破坏，召回率低   | ❌         |
| **连续字母数字当一个词**       | "HNSW 的 M 参数" → ["HNSW", "的", "M", "参数"] | 保留术语完整性 | 可能误判（如"iPhone15"）   | ✅         |

**为什么选"连续字母数字当一个词"？**

技术文档的特点：大量英文术语（HNSW、BM25、FAISS、pgvector）。这些术语必须作为**整体**参与 BM25 匹配，否则召回率极低。

**实现：**

```python
def _tokenize(text: str) -> list[str]:
    tokens = []
    current = []
    for char in text:
        if char.isalnum():  # 字母或数字
            current.append(char)
        else:
            if current:
                tokens.append("".join(current))  # 连续字母数字作为一个词
                current = []
            if not char.isspace():  # 中文字符
                tokens.append(char)  # 单字
    if current:
        tokens.append("".join(current))
    return tokens
```

**效果：**

- 输入："HNSW 的 M 参数是什么"
- 分词：`["HNSW", "的", "M", "参数", "是", "什", "么"]`
- BM25 匹配："HNSW" 作为整体，精确召回相关文档

**代码位置：** `store.py:48-66`

## 四、模块三：持久化 + 增量更新

### 4.1 问题背景

**旧版痛点：**

- 每次启动重新向量化 843 个 chunk
- 耗时 **54 秒** + 调用 **843 次** embedding API
- 语料未变时，这些开销纯属浪费

**需求：**

1. **持久化：** 语料未变时，直接加载索引，跳过 API 调用
2. **增量更新：** 修改 1 个文件时，只重建该文件的索引，其他保持不变

### 4.2 关键技术抉择

#### 抉择 1：持久化方案

| 方案                        | 优点                     | 缺点                       | 我们的选择 |
| --------------------------- | ------------------------ | -------------------------- | ---------- |
| **InMemoryVectorStore**     | 实现简单                 | 无法持久化，每次重启都重建 | ❌（已淘汰）|
| **Chroma (sqlite)**         | 本地嵌入式，单机部署     | 不支持分布式               | ✅         |
| **Pinecone / Weaviate**     | 云服务，开箱即用         | 需要网络，有成本           | ❌         |

**为什么选 Chroma？**

- 本地 sqlite，零依赖（不需要起额外服务）
- 支持按 metadata 增删改（增量更新的基础）
- 接口和 InMemoryVectorStore 一致，迁移成本低

**代码位置：** `store.py:199-216`

---

#### 抉择 2：指纹机制：总指纹 vs 文件级指纹

| 方案               | 粒度       | 增量更新支持 | 实现复杂度 | 我们的选择（演进路径） |
| ------------------ | ---------- | ------------ | ---------- | ---------------------- |
| **总指纹**         | 整体       | ❌           | 低         | ✅ M5a（持久化阶段）   |
| **文件级指纹**     | 每个文件   | ✅           | 中         | ✅ M7（增量更新阶段）  |
| **chunk 级指纹**   | 每个 chunk | ✅（更细粒度）| 高         | ❌（收益有限）         |

**演进路径：**

1. **M5a（持久化）：** 总指纹
   - 目标：避免"语料未变时重复向量化"
   - 方法：对所有 chunk 内容 + 模型版本计算一个 SHA256 哈希
   - 缺点：任何一个文件改动 → 全量重建

2. **M7（增量更新）：** 文件级指纹
   - 目标：修改 1 个文件时，只重建该文件的索引
   - 方法：每个文件独立计算哈希，存成 JSON
   - 效果：修改单文件，843 chunk → 52 chunk（94%↓）

**为什么不用 chunk 级指纹？**

| 维度         | 文件级指纹                     | chunk 级指纹                         |
| ------------ | ------------------------------ | ------------------------------------ |
| **实现复杂度** | 中（按文件分组，Chroma 按 source 删除） | 高（需维护 chunk id 映射，精确删除单个 chunk） |
| **收益**     | 修改 1 个文件 → 重建几十个 chunk | 修改 1 个 chunk → 重建 1 个 chunk    |
| **实际场景** | 修改文件时，往往会改多处       | 单 chunk 修改的场景极少              |

**权衡结论：** 文件级指纹已经能将增量更新成本降低 94%，chunk 级的边际收益不大，但复杂度显著增加。

**代码位置：**
- 总指纹：`store.py:90-110`
- 文件级指纹：`store.py:133-161`

#### 抉择 3：指纹内容覆盖范围

**问题：** 指纹应该包含哪些内容？

**方案对比：**

| 方案                     | 覆盖内容               | 缺陷                                     | 我们的选择 |
| ------------------------ | ---------------------- | ---------------------------------------- | ---------- |
| **只哈希文本内容**       | chunk.page_content     | 换模型后指纹不变，旧向量 + 新查询 = 错误结果 | ❌         |
| **文本 + 模型版本**      | content + model + dim  | 能感知模型变化，触发重建                 | ✅         |

**为什么必须包含模型版本？**

**典型 bug 场景：**

1. 用 `text-embedding-v3` 建了索引，指纹 = `abc123`
2. 换成 `text-embedding-v4`，语料没变，旧版指纹还是 `abc123`
3. 启动时判断"指纹一样" → 直接加载旧索引
4. **结果：** 旧向量（v3 空间）+ 新查询向量（v4 空间）→ 相似度计算是无意义的噪声，但**不报错**

**现在的方案：**

```python
def compute_fingerprint(chunks):
    hasher = hashlib.sha256()
    # 先哈希模型配置
    hasher.update(config.EMBEDDING_MODEL.encode("utf-8"))
    hasher.update(str(config.EMBEDDING_DIM or "default").encode("utf-8"))
    # 再哈希 chunk 内容
    for doc in sorted(chunks):
        hasher.update(doc.page_content.encode("utf-8"))
    return hasher.hexdigest()
```

**效果：** 换模型 → 指纹必然不同 → 触发重建，堵住静默失败风险。

**代码位置：** `store.py:96-100`

#### 抉择 4：BM25 增量更新 vs 全量重建

| 方案               | 优点                 | 缺点                               | 我们的选择 |
| ------------------ | -------------------- | ---------------------------------- | ---------- |
| **BM25 增量更新**  | 理论上更高效         | BM25Okapi 是内存结构，不支持增删改 | ❌         |
| **BM25 全量重建**  | 实现简单，无需适配   | 每次都重建所有 chunk               | ✅         |

**为什么 BM25 全量重建不是问题？**

| 对比维度     | 向量化（瓶颈）               | BM25 重建（不是瓶颈）       |
| ------------ | ---------------------------- | --------------------------- |
| **计算类型** | 网络 API 调用                | 纯 CPU 计算（本地）         |
| **耗时**     | 843 chunk → 54 秒            | 843 chunk → **几毫秒**      |
| **成本**     | 每次调用收费                 | 免费                        |

**结论：** 瓶颈在向量化（网络 API），不在 BM25。BM25 全量重建只需几毫秒，不值得为增量更新增加复杂度。

**代码位置：** `store.py:268-270`

### 4.3 增量更新流程

```python
def load_or_build_store(chunks):
    """智能判断：首次构建 / 增量更新 / 直接加载"""
    
    # 1. 检查索引是否存在
    if not (config.INDEX_DIR / "chroma.sqlite3").exists():
        # 首次构建
        return build_store(chunks)
    
    # 2. 计算文件级指纹
    old_fps = _load_file_fingerprints()  # 上次的指纹
    new_fps = compute_file_fingerprints(chunks)  # 当前的指纹
    
    # 3. 检测变化
    added, modified, deleted = detect_changes(old_fps, new_fps)
    changed_files = added + modified
    
    if not changed_files and not deleted:
        # 完全没变化 → 直接加载
        return load_existing_store(chunks)
    
    # 4. 有变化 → 增量更新
    vector_store = Chroma(persist_directory=str(config.INDEX_DIR))
    
    # 删除旧数据
    for source in deleted:
        vector_store.delete(where={"source": source})
    
    # 向量化新数据（只有变化文件的 chunk）
    new_chunks = [c for c in chunks if c.metadata["source"] in changed_files]
    vector_store.add_documents(new_chunks)
    
    # BM25 全量重建
    bm25 = _build_bm25_index(chunks)
    _save_bm25_index(bm25)
    
    # 保存新指纹
    _save_file_fingerprints(new_fps)
    
    return vector_store, bm25
```

## 五、模块四：Agent 架构 + 多轮记忆

### 5.1 问题背景

**旧版（固定 Chain）的局限：**

```python
# chain.py（已废弃）
def run_chain(question):
    # 固定流程：检索 → 拼提示词 → 调模型
    context = retrieve(question)  # 每次都无条件检索
    prompt = f"根据以下资料回答：{context}\n问题：{question}"
    return llm.invoke(prompt)
```

**痛点：**

1. **无条件检索：** 用户问"你有哪些笔记"，不需要检索，但 chain 还是会调一次检索 API
2. **无记忆：** 每次调用都是全新的，用户追问"它的参数是什么"，模型不知道"它"指什么
3. **不灵活：** 固定流程，无法根据问题类型自适应

### 5.2 关键技术抉择

#### 抉择 1：固定 Chain vs Agent

| 维度           | 固定 Chain                     | Agent（ReAct）                         | 我们的选择 |
| -------------- | ------------------------------ | -------------------------------------- | ---------- |
| **流程**       | 固定：检索 → 拼提示词 → 调模型 | 动态：模型决定是否调工具、调几次、何时停 | ✅ Agent   |
| **适应性**     | 低，无法根据问题类型调整       | 高，模型自主决策                       | ✅ Agent   |
| **记忆支持**   | 需要手动管理                   | LangGraph 原生支持 checkpointer        | ✅ Agent   |
| **实现复杂度** | 低                             | 中                                     | 可接受     |

**为什么选 Agent？**

**对比示例：**

| 用户提问                 | 固定 Chain                           | Agent（ReAct）                                     |
| ------------------------ | ------------------------------------ | -------------------------------------------------- |
| "HNSW 是什么"            | 调用检索 → 生成回答                  | 决策：需要检索 → 调用 search_notes → 生成回答     |
| "你有哪些笔记"           | 调用检索（浪费）→ 生成回答           | 决策：不需要检索 → 调用 list_notes → 直接返回清单 |
| "它的参数是什么"（追问） | 不知道"它"是什么 → 回答"请明确问题" | 从历史中理解"它"指 HNSW → 调用检索 → 生成回答     |

**代码位置：** `agent.py:43-52`

---

#### 抉择 2：多轮记忆存储介质

| 方案                  | 存储介质         | 跨进程 | 部署成本   | 适用场景       | 我们的选择（演进路径） |
| --------------------- | ---------------- | ------ | ---------- | -------------- | ---------------------- |
| **手写 messages 列表** | Python list      | ❌     | 零依赖     | 学习/演示      | ❌                     |
| **InMemorySaver**     | 进程内存（dict） | ❌     | 零依赖     | 单进程会话     | ✅ M5c（当前阶段）     |
| **SqliteSaver**       | sqlite 文件      | ✅     | 单机嵌入式 | 单机、多次启动 | ⏭️（未来计划）         |
| **PostgresSaver**     | Postgres 数据库  | ✅     | 需起服务   | 多用户、生产   | ⏭️（生产环境）         |

**为什么当前选 InMemorySaver？**

1. **当前目标：** 验证"多轮记忆"能力，不需要跨进程存活
2. **零依赖：** 不用起任何额外存储服务
3. **接口一致性：** 所有 Saver 的接口完全一致，以后换只改一行：

```

**代码位置：** `agent.py:51`

#### 抉择 3：多轮记忆的本质

**必须先接受的事实：LLM 本身没有记忆**

LLM API 每次调用都是**无状态**的：你传一个 `messages` 列表，模型只根据**这一次收到的列表**生成回复。

**"多轮记忆"的本质：** 客户端把历史存起来，下一轮把"历史 + 新问题"拼在一起再发一遍。

```python
第 1 轮：messages = [system, user: "HNSW 是什么"]
                  → assistant: "HNSW 是..."

第 2 轮：messages = [system, 
                    user: "HNSW 是什么", 
                    assistant: "HNSW 是...",
                    user: "它的参数怎么调"]  # ← 完整历史重新发送
                  → assistant: "M / ef_construction / ..."
```

**checkpointer 的职责：** 自动化"存历史、拼历史"：

- 每次 `invoke` 之后把当前的 `messages` 状态存一份
- 下次同一个 `thread_id` 再 `invoke` 时，先取出存的状态，再把新消息追加上去

**代码位置：** `agent.py:12-16`（注释说明）

---

#### 抉择 4：thread_id 是关键

**thread_id 的作用：** "这是哪个会话"的身份证。

```python
# main.py
thread_id = uuid.uuid4().hex  # 整个进程共用一个 thread_id

while True:
    question = input("你: ")
    answer = ask(agent, question, thread_id)  # 同一个 thread_id
    print(f"\n{answer}\n")
```

**同一个 thread_id 连续调用 → 历史会自动累加**
**换一个 thread_id → 全新对话，跟之前的互不干扰**

**为什么在 main.py 里生成，而不是在 agent.py 里？**

- `main.py` 负责会话管理，它知道"这是同一次启动"
- `agent.py` 只负责"回答单个问题"，不关心会话边界
- 职责清晰，低耦合

**代码位置：**
- 生成 thread_id：`main.py:35`
- 使用 thread_id：`agent.py:61`

### 5.5 已知局限与改进方向

| 局限                           | 影响                           | 改进方向                                 |
| ------------------------------ | ------------------------------ | ---------------------------------------- |
| **历史不持久化**               | 进程退出，历史全丢             | 换成 SqliteSaver / PostgresSaver         |
| **没有历史长度控制**           | 对话越长，每次请求 token 越多  | 滑动窗口 / 历史摘要 / 检索式记忆         |
| **单进程假设**                 | 不支持多用户会话隔离           | 多进程部署 + 持久化 checkpointer         |

**代价分析：**

对话轮数越多，每次请求的 token 数线性增长：

| 轮次 | 累计 token | 成本（¥0.001/1k token） |
| ---- | ---------- | ----------------------- |
| 1    | ~500       | ¥0.0005                 |
| 5    | ~2,500     | ¥0.0025                 |
| 10   | ~5,000     | ¥0.005                  |
| 20   | ~10,000    | ¥0.01                   |

**实际系统的三种解决方案：**

1. **滑动窗口：** 只保留最近 N 轮（简单，但会丢失早期上下文）
2. **摘要压缩：** 定期把老消息用 LLM 压缩成摘要（保留信息密度，但压缩本身要调一次模型）
3. **检索式记忆：** 把历史消息也做成向量存起来，每轮只检索"和当前问题最相关的历史片段"（推荐，长对话场景下最现代的方案）

## 八、面试高频问题

### Q1：为什么标题路径必须在 page_content 而不是 metadata？

**A：** metadata 不参与向量计算。

```python
# 向量化过程
embedding = embed_model(doc.page_content)  # 只用 page_content
# metadata 完全不参与
```

如果标题路径只在 metadata 里：
- 用户问"考勤制度"
- 这一块的 `page_content` 里没有"考勤"两个字
- 向量根本不包含"考勤"的语义 → 搜不到

**正确做法：** 标题路径必须拼进 `page_content`，metadata 只用于过滤（如 `where={"source": "xx.md"}`）和展示引用来源。

---

### Q2：为什么代码块保护用状态机而不是正则？

**A：** Markdown 代码块是成对出现的，必须追踪状态。

如果用正则 `re.findall(r'```.*?```', text, re.DOTALL)` 提前匹配：
- 遇到未闭合的代码块会匹配失败
- 嵌套代码块会匹配错位

**状态机的优势：** 逐行扫描，遇到 ``` 就翻转状态，天然处理未闭合和嵌套情况，鲁棒性更强。

---

### Q3：为什么 RRF 的 k=60？

**A：** 经验值，来自论文 *Reciprocal Rank Fusion outperforms Condorcet*。

k 是平滑参数，防止排名 1 的权重过大：

```
k=60:
rank=1: 1/(60+1) = 0.016
rank=2: 1/(60+2) = 0.016
rank=5: 1/(60+5) = 0.015

k=0（无平滑）:
rank=1: 1/1 = 1.0
rank=2: 1/2 = 0.5   ← 权重断崖式下降
```

**k 越大** → 排名差异的权重差越小，更"平等"  
**k 越小** → 头部排名的权重越大，更"集中"

k=60 是论文实验得出的最佳实践值，大多数场景下效果最好。

---

### Q4：为什么增量更新是文件级而不是 chunk 级？

**A：** 权衡取舍。

| 维度         | 文件级指纹                         | chunk 级指纹                             |
| ------------ | ---------------------------------- | ---------------------------------------- |
| **实现复杂度** | 中（按文件分组，Chroma 按 source 删除） | 高（需维护 chunk id 映射，精确删除单个 chunk） |
| **收益**     | 修改 1 个文件 → 重建几十个 chunk   | 修改 1 个 chunk → 重建 1 个 chunk        |
| **实际场景** | 修改文件时，往往会改多处           | 单 chunk 修改的场景极少                  |

**实测验证：** 修改单文件（52 个 chunk），从 843 chunk 降到 52 chunk，已经是 94% 的提升，chunk 级的边际收益不大。

---

### Q5：为什么 embedding 模型要加入指纹？

**A：** 防止"换模型但语料没变，指纹检测不到"的静默 bug。

**场景：**
1. 用 `text-embedding-v3` 建了索引，指纹 = `abc123`
2. 换成 `text-embedding-v4`，语料没变，旧版指纹还是 `abc123`
3. 启动时判断"指纹一样" → 直接加载旧索引
4. **结果：** 旧向量（v3 空间）+ 新查询向量（v4 空间）→ 相似度计算是无意义的噪声，但不报错

**现在的方案：**

```python
fingerprint = hash(模型名称 + 模型维度 + chunk 内容)
```

换模型 → 指纹必然不同 → 触发重建，堵住静默失败风险。

---

### Q6：为什么 BM25 全量重建而不是增量更新？

**A：** 瓶颈不在 BM25。

| 对比维度     | 向量化（瓶颈）       | BM25 重建（不是瓶颈） |
| ------------ | -------------------- | --------------------- |
| **计算类型** | 网络 API 调用        | 纯 CPU 计算（本地）   |
| **耗时**     | 843 chunk → 54 秒    | 843 chunk → 几毫秒    |
| **成本**     | 每次调用收费         | 免费                  |

**结论：** BM25 重建只需几毫秒，不值得为增量更新增加复杂度。

---

### Q7：多轮记忆的成本问题怎么解决？

**A：** 对话越长，每轮重发的历史越多，token 数线性增长。

实际系统的三种解决方案：

1. **滑动窗口**：只保留最近 N 轮，超出的直接丢弃（简单，但会丢失早期上下文）
2. **摘要压缩**：定期把老消息用 LLM 压缩成摘要（保留信息密度，但压缩本身要调一次模型）
3. **检索式记忆**（推荐）：把历史消息也做成向量存起来，每轮只检索"和当前问题最相关的历史片段"拼进上下文（把"记忆问题"转化成"检索问题"，长对话场景下更现代的方案）

---

### Q8：为什么 agent 架构比固定 chain 更适合多轮记忆？

**A：** 决策能力 + 状态管理。

**固定 chain：**

```
检索 → 拼提示词 → 调模型
```

- 固定线性流程，每次都无条件检索
- 多轮记忆可以加（手动拼历史），但要自己管

**agent 架构：**

```
model 节点 ↔ tools 节点（循环）
```

- 模型自己决定要不要调用工具、调用几次、什么时候停
- `checkpointer` 是状态图原生支持的能力，把"记住历史"和"决策要不要调工具"统一管理

**例子：**

```
你: HNSW 是什么
   → agent 决策：调用 search_docs 工具 → 找到文档 → 回答

你: 它的参数怎么调
   → agent 决策：上一轮已经拿到 HNSW 文档，不需要再检索，直接从历史里提取回答
```

固定 chain 做不到这种"根据历史决定是否检索"的优化，必然每轮都调一次检索。

---

### Q9：BM25 的分词为什么要"保留连续字母数字"？

**A：** 专有名词识别。

**如果纯单字切分：**

```
"HNSW 的 M 参数" -> ["H", "N", "S", "W", "的", "M", "参数"]
```

用户问"HNSW" → BM25 会召回所有包含 "H" / "N" / "S" / "W" 的文档，召回率 100% 但精确率极低。

**连续字母数字当一个词：**

```
"HNSW 的 M 参数" -> ["HNSW", "的", "M", "参数"]
```

用户问"HNSW" → BM25 精确匹配 "HNSW" 这个词，精确率高。

**这是中文 + 技术文档的最佳实践**：中文单字切分（因为中文词边界不明确），但保留英文术语的完整性。

---

### Q10：如果文件重命名会怎样？

**A：** 被识别为"删除 + 新增"，会重新向量化。

**原因：** 文件级指纹用 `metadata["source"]`（文件名）作为 key：

```python
fingerprints = {
    "12-补充-检索与RAG.md": "abc123",
    "13-向量数据库.md": "def456",
}
```

重命名后：
- 旧文件名在新指纹里不存在 → 被认为是"删除"
- 新文件名在旧指纹里不存在 → 被认为是"新增"

**是否可接受？**

✅ 可接受。文件名是 metadata 的一部分，重命名后确实需要重新向量化（因为标题前缀里包含文件名）。

    6. RRF 的 k=60

    为什么 RRF 融合的 k=60？

    RRF 公式：
    RRF_score(doc) = Σ 1 / (k + rank_in_each_list)

    k 的作用： 平滑参数，防止排名 1 的权重过大

    ┌─────┬────────┬────────┬──────────────────────────────┐  
    │ k   │ rank=1 │ rank=2 │                              │  
    │ 值  │        │        │             特点             │  
    │     │ 的权重 │ 的权重 │                              │  
    ├─────┼────────┼────────┼──────────────────────────────┤  
    │ 0   │ 1.0    │ 0.5    │ 头部权重极大，断崖式下降     │  
    ├─────┼────────┼────────┼──────────────────────────────┤  
    │ 10  │ 0.091  │ 0.083  │ 头部权重较大                 │  
    ├─────┼────────┼────────┼──────────────────────────────┤  
    │ 60  │ 0.016  │ 0.016  │ 排名差异的权重差小，更"平等" │  
    ├─────┼────────┼────────┼──────────────────────────────┤  
    │ 100 │ 0.010  │ 0.010  │ 排名差异几乎忽略             │  
    └─────┴────────┴────────┴──────────────────────────────┘  

    我的选择：k=60

    理由：
    1. 论文经验值：来自 Reciprocal Rank Fusion outperforms    
       Condorcet，实验得出的最佳值
    2. 平衡性好：既不会让头部文档独占，也不会让排名完全失去意 
       义
    3. 无需调参：适用绝大多数场景，鲁棒性强

    直觉理解：
    - k 太小（如 k=0）：排名 1 的文档权重 1.0，排名 2
      的文档权重 0.5，差距过大。如果向量检索的排名 1
      刚好是个噪声（相似度虚高），就会主导最终结果。
    - k 太大（如 k=100）：排名 1 和排名 20 的权重差只有       
      0.002，排名几乎没意义，退化成"只要出现就行"。
    - k=60：排名 1 的权重 0.016，排名 20 的权重
      0.0125，差距适中。在两路都排前面的文档能脱颖而出，但不会
      被单路的头部独占。

    面试追问应对：

    ▎ Q: k=60 适合所有场景吗？有没有考虑过调整？
    ▎ A: 60
    ▎ 是论文实验得出的最佳实践值，适用大多数场景。如果实际业务
    ▎ 中发现"混合检索的效果不如单一向量检索"，可以考虑调整：  
    ▎ - 提高 k（如 80-100）：让排名的影响更小，适合"两路召回结
    ▎ 果差异很大"的场景
    ▎ - 降低 k（如 20-40）：让头部排名的权重更大，适合"向量检 
    ▎ 索质量很高，BM25 只是补充"的场景
    ▎
    ▎ 实际调优需要准备评估集，测试不同 k
    ▎ 值对准确率的影响。但当前 k=60 的效果已经很好（准确率    
    ▎ +30%），没必要过早优化。

    7. FETCH_K=20, TOP_K=5

    为什么第一阶段召回 20 个，第二阶段返回 5 个？

    两阶段检索策略：
    FETCH_K = 20  # 第一阶段：每路召回 20 个
    TOP_K = 5     # 第二阶段：融合后取前 5 个

    为什么不直接召回 5 个？

    ┌────────┬────────────────────────────────────────────┐   
    │  方案  │                    问题                    │   
    ├────────┼────────────────────────────────────────────┤   
    │ 直接召 │ 两路重叠度低时，RRF 融合会让"只在单路出现  │   
    │ 回 5   │ 的文档"分数过低，导致最终 top-5            │   
    │ 个     │ 都是"双路都有但排名不高"的文档             │   
    ├────────┼────────────────────────────────────────────┤   
    │ 召回   │ 给融合算法足够选择空间，在两路都排前面的文 │   
    │ 20 个  │ 档能脱颖而出                               │   
    │ 再融合 │                                            │   
    └────────┴────────────────────────────────────────────┘   

    具体例子：

    假设用户问"BM25 公式"：
    - 向量检索 top-5：相似度召回了"检索算法综述""信息检索基础"
      等泛化文档
    - BM25 检索 top-5：精确匹配召回了"BM25 原理""BM25
      参数调优"等相关文档
    - 两路重叠：可能只有 1 个文档重叠

    如果直接融合 top-5，RRF 会给重叠的 1 个文档高分，其他 4   
    个文档分数分散。但真正相关的"BM25
    参数调优"可能在向量检索的第 10 名、BM25 检索的第 3        
    名——直接召回 5 个就漏掉了。

    召回 20 个再融合：
    - 向量检索 top-20：包含了"BM25 参数调优"（排名 10）       
    - BM25 检索 top-20：包含了"BM25 参数调优"（排名 3）       
    - RRF 融合：1/(60+10) + 1/(60+3) = 0.014 + 0.016 =        
      0.030（高分）
    - 最终 top-5：包含了"BM25 参数调优"

    为什么返回 5 个而不是 10 个？

    ┌──────┬────────────────────┬────────────────┬────────┐   
    │ TOP_ │        优点        │      缺点      │ 我的选 │   
    │  K   │                    │                │   择   │   
    ├──────┼────────────────────┼────────────────┼────────┤   
    │ 3    │ 结果紧凑，LLM      │ 可能漏掉重要信 │ ❌     │   
    │      │ 理解快             │ 息             │        │   
    ├──────┼────────────────────┼────────────────┼────────┤   
    │ 5    │ 平衡信息完整性和简 │ —              │ ✅     │   
    │      │ 洁性               │                │        │   
    ├──────┼────────────────────┼────────────────┼────────┤   
    │      │                    │ 引入噪声，LLM  │        │   
    │ 10   │ 信息更全           │ 上下文过长（~1 │ ❌     │   
    │      │                    │ 800 字）       │        │   
    └──────┴────────────────────┴────────────────┴────────┘   

    实测：
    - 5 个文档 ~900 字，LLM 生成的回答质量高、引用准确        
    - 10 个文档 ~1800 字，LLM
      容易"迷失"在大量信息里，回答质量下降

    面试追问应对：

    ▎ Q: FETCH_K=20 是怎么定的？有做过实验吗？
    ▎ A: 20 是参考了混合检索论文的经验值。理论上 FETCH_K      
    ▎ 越大，融合的选择空间越充足，但也会引入更多噪声。实测 20 
    ▎ 是个平衡点——召回覆盖率高，计算量可接受（向量检索 20 个  
    ▎ ~10ms，BM25 检索 20 个 ~5ms）。如果要严格优化，可以测试 
    ▎ 10/15/20/30 对准确率的影响，但当前 20 的效果已经很好。

    8. 指纹包含模型版本

    为什么指纹要包含 embedding 模型名称和维度？

    指纹计算逻辑：
    def compute_fingerprint(chunks):
        hasher = hashlib.sha256()
        # 先哈希模型配置
        hasher.update(config.EMBEDDING_MODEL.encode("utf-8")) 
        hasher.update(str(config.EMBEDDING_DIM or
    "default").encode("utf-8"))
        # 再哈希 chunk 内容
        for doc in sorted(chunks):
            hasher.update(doc.page_content.encode("utf-8"))   
        return hasher.hexdigest()

    为什么要包含模型配置？

    典型 bug 场景（防御性设计）：

    1. 用 text-embedding-v3 建了索引，指纹 = abc123
    2. 换成 text-embedding-v4，语料没变，如果指纹不包含模型版 
       本，旧指纹还是 abc123
    3. 启动时判断"指纹一样" → 直接加载旧索引
    4. 结果： 旧向量（v3 空间，1024 维）+ 新查询向量（v4      
       空间，1024 维）
    5. 后果： 相似度计算是无意义的噪声（两个向量空间不同），但
       不报错，静默失败

    现在的方案：
    - 指纹 = hash(模型名 + 模型维度 + chunk 内容)
    - 换模型 → 指纹必然不同 → 触发重建
    - 堵住静默失败风险

    面试追问应对：

    ▎ Q: 如果只换了模型参数（如
    ▎ temperature），需要重建索引吗？
    ▎ A: 不需要。temperature 是生成参数，只影响对话模型（如   
    ▎ DeepSeek），不影响 embedding 模型。embedding
    ▎ 模型是确定性的（相同输入 → 相同向量），不受 temperature 
    ▎ 影响。指纹只包含 embedding
    ▎ 相关的配置（模型名、维度），不包含对话模型的配置。      

    ▎ Q: 如果模型升级了（v3 →
    ▎ v4），但向量空间兼容，也要重建吗？
    ▎ A: 是的，保守起见必须重建。因为模型升级后，即使维度相同 
    ▎ ，向量的分布可能变化（如 v4 对中文的理解更好，相似度计算
    ▎ 的结果会不同）。如果模型提供商明确说明"v3 和 v4
    ▎ 的向量空间兼容"，可以跳过重建，但这种情况很少见。
