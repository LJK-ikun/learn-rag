# 07 增量更新

## 为什么需要增量更新

### 问题

之前的实现是"全量重建"：

```python
# 旧版：一个总指纹
fingerprint.txt: "39cedafb3589..."
```

**后果：**
- 改 1 个字 → 重建 843 个 chunk → 等 54 秒 + 调用 843 次 embedding API
- 规模大了（几千到几万文件）完全不可接受

### 解决方案

**文件级指纹 + 增量更新**

```python
# 新版：每个文件一个指纹
file_fingerprints.json:
{
  "12-补充-检索与RAG.md": "a3f2e1...",
  "08-前端面试.md": "b7d4c9...",
  ...
}
```

启动时对比新旧指纹：
- 文件没变 → 跳过
- 文件变了 → 只重建这个文件的 chunk

**步骤：**
1. **删除旧数据**：`vector_store.delete(where={"source": filename})`

3. **重建 BM25**：全量重建（纯 CPU，毫秒级）

## 主流程改造

### 旧版逻辑（2 种情况）

```python
if 总指纹一样:
    加载索引
else:
    全量重建
```

### 新版逻辑（3 种情况）

```python
if 索引不存在:
    全量构建
elif 所有文件指纹都一样:
    直接加载
else:
    增量更新（只处理变化的文件）
```

## 技术细节

### Q1: 为什么 BM25 是全量重建？

**A:** BM25 是内存中的数据结构（`rank_bm25.BM25Okapi`），不像 Chroma 有数据库支持增删改。

**但这不是问题：**
- BM25 重建是纯 CPU 计算，不联网
- 843 个 chunk 重建只需几毫秒
- 瓶颈在向量化（网络 API 调用），不在 BM25

### Q2: 如果文件重命名会怎样？

**A:** 会被识别为"删除旧文件 + 新增新文件"，会重新向量化一次。

**这是可接受的：**
- 文件名是 metadata 的一部分
- 重命名确实需要更新 metadata

### Q3: 如果切分参数变了（MAX_CHARS）？

**A:** 需要全量重建。当前实现会自动触发，因为：
- 切分参数变 → chunk 数量/内容变 → 文件指纹变
- 所有文件指纹都变 → 触发全量更新

**未来优化：** 可以把切分参数也加入指纹，明确提示"参数变了，需全量重建"

## 边界情况处理

### 1. 首次运行（旧版升级）

**现象：** `file_fingerprints.json` 不存在

**行为：** 把所有文件当成"新增"，全量重建一次，之后就是增量了

### 2. 文件被删除

**检测：** 旧指纹有，新指纹没有

**行为：** 从向量库删除该文件的所有 chunk

### 3. 模型换了

**检测：** 指纹包含模型名称，模型变了指纹必变

**行为：** 所有文件指纹都变 → 触发全量重建（符合预期）

## 下一步优化方向

### 1. 并行向量化

当前是串行向量化 chunk，可以改成批量并发：

```python
# 当前
for chunk in new_chunks:
    embed(chunk)  # 一次一个

# 优化
embeddings = embed_batch(new_chunks)  # 一次一批
```

### 2. 更细粒度：chunk 级指纹

当前是文件级，改 1 个字 → 重建整个文件的所有 chunk

**可以优化到 chunk 级：**
- 给每个 chunk 算一个指纹
- 只重建变化的 chunk

**代价：**
- 复杂度显著增加
- 收益有限（大部分情况下整个文件都会改）

### 3. 指纹包含切分参数

```python
fingerprint = hash(模型名称 + MAX_CHARS + OVERLAP + 文件内容)
```

好处：切分参数变了能明确提示，而不是静默触发全量重建。
